# Refactoring AI-Generated Code

Systematic refactoring of an LLM-generated Java/Spring Boot codebase: code smell detection, test-safe transformation, and before/after metric validation.

**Course:** Engineering Design II – Project 02: Refactoring AI-Generated Code (Sustainable Software Engineering)

## Project Overview

Large language models can produce working code in minutes, but that code often carries technical debt: duplication, high cyclomatic complexity, weak modularity and bloated classes. This project takes a codebase generated by an LLM under a documented protocol, locks its behavior with tests, refactors it in small verified steps, and proves the maintainability gains with metrics.

### Research Questions

- **RQ1:** Which code smells and technical debt patterns appear in an LLM-generated codebase, and how do revision rounds increase them?
- **RQ2:** How much does test-safe, systematic refactoring improve maintainability metrics without changing behavior?
- **RQ3 (optional):** Under the same tests, how does manual refactoring compare with LLM-assisted refactoring?

### Subject Application

A simple **course and absence tracking REST API** (Java, Spring Boot, H2 in-memory database).

| Entity | Description |
| --- | --- |
| Student | Basic student information |
| Course | Course information and type (theoretical / practical) |
| Absence | Absence records per student and course |
| Grade | Midterm, final and optional project grades per student and course |

Features:

1. Student and course management (create, list, update, delete)
2. Absence tracking with status calculation (Normal / Warning / Failed); limits differ for theoretical and practical courses
3. Grade calculation with two weighting schemes (midterm/final and midterm/project/final) and letter grade
4. Student report listing courses, grades and absence status

### Business Rules

**Absence** (14-week semester, 3 hours per week, 42 hours in total):

| Course type | Limit | Allowed absence | Warning from | Failed when |
| --- | --- | --- | --- | --- |
| Theoretical | 30% | 13 hours | 10 hours | > 13 hours |
| Practical | 20% | 9 hours | 6 hours | > 9 hours |

**Grade weighting:**

| Course | Midterm | Project | Final |
| --- | --- | --- | --- |
| Without project | 40% | – | 60% |
| With project | 30% | 30% | 40% |

**Letter grades** (passing grade 40):

| AA | BA | BB | CB | CC | DC | DD | FF |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 85–100 | 78–84 | 70–77 | 63–69 | 55–62 | 48–54 | 40–47 | 0–39 |

## Methodology

1. **Generation:** The codebase is generated feature by feature by an LLM; every prompt and revision is logged.
2. **Baseline measurement:** All metrics are recorded on the `v0-ai-baseline` tag.
3. **Behavior locking:** Characterization tests capture the current behavior before any change.
4. **Safe refactoring:** One refactoring per pull request, using IDE-supported transformations, verified by tests in CI.
5. **Before/after comparison:** Metrics are compared against the baseline and the applied refactorings are documented with RefactoringMiner.

## Workflow

- `main` is protected; every change goes through a pull request with at least one approval.
- Pull requests are squash-merged, so each commit on `main` represents one change (ideally one refactoring).
- Branch naming: `generation/`, `test/`, `refactor/`, `fix/`, `metrics/`, `docs/`, `chore/`
- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/) (e.g. `refactor: extract grade weighting into strategy classes (#14)`).
