# API Contract

This document is the single source of truth for the **externally visible behavior** of the application that the three LLMs generate. All three codebases must expose exactly these endpoints, fields, status codes and business rules, so that one shared API test suite can run against every codebase.

The contract defines **what** the API does, never **how** it is built. It does not prescribe classes, layers, packages (other than the root package), libraries for business logic, or naming of internal code. Those choices are left to each LLM and are part of what this project studies.

The prompts in [`prompts/`](prompts/) contain the relevant parts of this contract word for word. If this document and a prompt ever differ, fix the prompt **before** generation starts; never after.

## 1. Common rules

### 1.1 Technical frame

| Item | Value |
| --- | --- |
| Language and runtime | Java 17 or newer |
| Framework | Spring Boot 3.x |
| Build | Maven; `mvn package` must succeed and `mvn spring-boot:run` must start the application |
| Coordinates | groupId `edu.abu`, artifactId `course-tracker` |
| Root package | `edu.abu.coursetracker`; the `@SpringBootApplication` class is in this package |
| Database | H2 in-memory; data does not need to survive a restart |
| Port | 8080 |
| API documentation | Swagger UI at `/swagger-ui.html` (springdoc-openapi) |
| Out of scope | Authentication, user interface, external services |

### 1.2 Conventions

- Base path for all endpoints: `/api`
- Request and response bodies are JSON (`application/json`), UTF-8.
- JSON field names use camelCase exactly as written in this contract.
- Unknown fields in a request body are ignored.
- Identifiers (`id`, `studentId`, `courseId`, …) are positive integers generated by the server. An `id` sent in a request body is ignored.
- Dates use ISO format `YYYY-MM-DD`.
- Lists are returned as JSON arrays (never wrapped in an object) unless stated otherwise. An empty list is `[]`.

### 1.3 Status codes

| Code | When |
| --- | --- |
| 200 OK | Successful read or update |
| 201 Created | Successful creation; the body contains the created resource |
| 204 No Content | Successful delete; empty body |
| 400 Bad Request | Validation failure, malformed JSON, invalid enum value, wrong type, or a non-numeric path id |
| 404 Not Found | A resource referenced by the path does not exist |
| 409 Conflict | Uniqueness violation or a change that conflicts with existing data |

**Precedence:** if a path refers to a resource that does not exist, the response is **404**, even if the request body is also invalid.

### 1.4 Error body

Every 400, 404 and 409 response has this body:

```json
{
  "status": 404,
  "error": "Not Found",
  "message": "Student with id 42 not found"
}
```

| Field | Type | Content |
| --- | --- | --- |
| `status` | integer | The HTTP status code |
| `error` | string | The standard reason phrase: `Bad Request`, `Not Found` or `Conflict` |
| `message` | string | A human-readable, non-empty explanation |

The exact wording of `message` is free. Tests only check `status`, `error` and that `message` is not empty.

## 2. Students

### 2.1 Fields

| Field | Type | In request | Rules |
| --- | --- | --- | --- |
| `id` | integer | ignored | Generated by the server |
| `studentNumber` | string | required | Exactly 9 digits (`0`–`9`); unique across all students |
| `firstName` | string | required | Not blank; at most 50 characters |
| `lastName` | string | required | Not blank; at most 50 characters |
| `email` | string | required | A well-formed email address |

Response example:

```json
{
  "id": 1,
  "studentNumber": "220201001",
  "firstName": "Ayşe",
  "lastName": "Yılmaz",
  "email": "ayse.yilmaz@example.com"
}
```

### 2.2 Endpoints

| Method and path | Request body | Success | Errors |
| --- | --- | --- | --- |
| `POST /api/students` | Student fields | 201, created student | 400 invalid; 409 `studentNumber` already used |
| `GET /api/students` | — | 200, all students sorted by `id` ascending | — |
| `GET /api/students/{id}` | — | 200, the student | 404 |
| `PUT /api/students/{id}` | Student fields (full replacement) | 200, updated student | 404; 400 invalid; 409 `studentNumber` used by another student |
| `DELETE /api/students/{id}` | — | 204 | 404 |

Deleting a student also deletes all of that student's absence records and grades.

## 3. Courses

### 3.1 Fields

| Field | Type | In request | Rules |
| --- | --- | --- | --- |
| `id` | integer | ignored | Generated by the server |
| `code` | string | required | 2–10 characters, only uppercase letters `A`–`Z` and digits; unique across all courses |
| `name` | string | required | Not blank; at most 100 characters |
| `type` | string (enum) | required | `THEORETICAL` or `PRACTICAL` |
| `weeklyHours` | integer | required | 1 to 10 inclusive |
| `gradingScheme` | string (enum) | required | `MIDTERM_FINAL` or `MIDTERM_PROJECT_FINAL` (DT1 adds `PROJECT_ONLY`) |

DT2 adds one more field, `absenceLimitPercent`; see section 8.

Response example:

```json
{
  "id": 1,
  "code": "SE402",
  "name": "Engineering Design II",
  "type": "THEORETICAL",
  "weeklyHours": 3,
  "gradingScheme": "MIDTERM_PROJECT_FINAL"
}
```

### 3.2 Endpoints

| Method and path | Request body | Success | Errors |
| --- | --- | --- | --- |
| `POST /api/courses` | Course fields | 201, created course | 400 invalid; 409 `code` already used |
| `GET /api/courses` | — | 200, all courses sorted by `id` ascending | — |
| `GET /api/courses/{id}` | — | 200, the course | 404 |
| `PUT /api/courses/{id}` | Course fields (full replacement) | 200, updated course | 404; 400 invalid; 409 `code` used by another course; 409 `gradingScheme` changed while the course has at least one grade |
| `DELETE /api/courses/{id}` | — | 204 | 404 |

Deleting a course also deletes all absence records and grades for that course.

Changing `type` or `weeklyHours` with `PUT` is allowed. Existing absence records are kept unchanged; absence status is always calculated from the current course values.

## 4. Absences and absence status

There is no enrollment step. Absences can be recorded for any existing student in any existing course.

### 4.1 Absence record fields

| Field | Type | In request | Rules |
| --- | --- | --- | --- |
| `id` | integer | ignored | Generated by the server |
| `studentId` | integer | ignored (taken from the path) | — |
| `courseId` | integer | ignored (taken from the path) | — |
| `date` | string (date) | required | A valid date in `YYYY-MM-DD` format |
| `hours` | integer | required | At least 1 and at most the course's `weeklyHours` |

Several records may have the same date.

Response example:

```json
{
  "id": 7,
  "studentId": 1,
  "courseId": 1,
  "date": "2026-10-12",
  "hours": 2
}
```

### 4.2 Endpoints

| Method and path | Request body | Success | Errors |
| --- | --- | --- | --- |
| `POST /api/students/{studentId}/courses/{courseId}/absences` | `{ "date", "hours" }` | 201, created record | 404 student or course; 400 invalid |
| `GET /api/students/{studentId}/courses/{courseId}/absences` | — | 200, records sorted by `date` ascending, then `id` ascending | 404 student or course |
| `DELETE /api/students/{studentId}/courses/{courseId}/absences/{absenceId}` | — | 204 | 404 student, course or record; 404 if the record belongs to a different student or course |
| `GET /api/students/{studentId}/courses/{courseId}/absence-status` | — | 200, absence status | 404 student or course |

### 4.3 Absence status response

```json
{
  "studentId": 1,
  "courseId": 1,
  "totalCourseHours": 42,
  "allowedAbsenceHours": 13,
  "totalAbsenceHours": 10,
  "remainingAbsenceHours": 3,
  "status": "WARNING"
}
```

### 4.4 Calculation rules

Let `semesterWeeks`, `theoreticalLimitPercent`, `practicalLimitPercent` and `warningMarginHours` be the configuration values in section 4.5.

1. `totalCourseHours` = `weeklyHours` × `semesterWeeks`
2. `limitPercent` = `theoreticalLimitPercent` for `THEORETICAL` courses, `practicalLimitPercent` for `PRACTICAL` courses (DT2 adds a per-course override)
3. `allowedAbsenceHours` = `totalCourseHours` × `limitPercent` / 100, **rounded up** to the next whole number. The result must be exact: 42 × 30 / 100 = 12.6 → 13; 42 × 20 / 100 = 8.4 → 9; 70 × 20 / 100 = 14 → 14.
4. `totalAbsenceHours` = sum of `hours` of all records of this student in this course; 0 if there are none
5. `remainingAbsenceHours` = `allowedAbsenceHours` − `totalAbsenceHours`, but never below 0
6. `status`:
   - `FAILED` if `totalAbsenceHours` > `allowedAbsenceHours`
   - otherwise `WARNING` if `totalAbsenceHours` > 0 **and** `allowedAbsenceHours` − `totalAbsenceHours` ≤ `warningMarginHours`
   - otherwise `NORMAL`

Examples with default configuration:

| Course | `totalCourseHours` | `allowedAbsenceHours` | `totalAbsenceHours` → `status` |
| --- | --- | --- | --- |
| THEORETICAL, 3 h/week | 42 | 13 | 0 → NORMAL · 9 → NORMAL · 10 → WARNING · 13 → WARNING · 14 → FAILED |
| PRACTICAL, 3 h/week | 42 | 9 | 5 → NORMAL · 6 → WARNING · 9 → WARNING · 10 → FAILED |
| THEORETICAL, 1 h/week | 14 | 5 | 1 → NORMAL · 2 → WARNING · 5 → WARNING · 6 → FAILED |
| PRACTICAL, 1 h/week | 14 | 3 | 0 → NORMAL · 1 → WARNING · 3 → WARNING · 4 → FAILED |

### 4.5 Configuration

These values must be read from `application.properties` and must be changeable there without changing code:

```properties
coursetracker.semester-weeks=14
coursetracker.absence.theoretical-limit-percent=30
coursetracker.absence.practical-limit-percent=20
coursetracker.absence.warning-margin-hours=3
```

## 5. Grades

A student has at most one grade per course. As with absences, there is no enrollment step.

### 5.1 Request

`PUT /api/students/{studentId}/courses/{courseId}/grade`

```json
{
  "midterm": 55,
  "finalExam": 50,
  "project": 50
}
```

| Field | Type | Rules |
| --- | --- | --- |
| `midterm` | integer or null | 0 to 100 inclusive when present |
| `finalExam` | integer or null | 0 to 100 inclusive when present |
| `project` | integer or null | 0 to 100 inclusive when present |

Which fields are required depends on the course's `gradingScheme`. A field that is absent from the JSON counts as `null`.

| `gradingScheme` | `midterm` | `finalExam` | `project` |
| --- | --- | --- | --- |
| `MIDTERM_FINAL` | required | required | must be null |
| `MIDTERM_PROJECT_FINAL` | required | required | required |
| `PROJECT_ONLY` (DT1) | must be null | must be null | required |

A missing required field, a value that must be null but is not, or a value outside 0–100 → **400**.

### 5.2 Endpoints

| Method and path | Request body | Success | Errors |
| --- | --- | --- | --- |
| `PUT /api/students/{studentId}/courses/{courseId}/grade` | Grade fields | 200, grade result; creates the grade or replaces the existing one | 404 student or course; 400 invalid |
| `GET /api/students/{studentId}/courses/{courseId}/grade` | — | 200, grade result | 404 student or course; 404 no grade recorded yet |

### 5.3 Grade result response

```json
{
  "studentId": 1,
  "courseId": 1,
  "gradingScheme": "MIDTERM_PROJECT_FINAL",
  "midterm": 55,
  "finalExam": 50,
  "project": 50,
  "average": 52,
  "letterGrade": "DC",
  "passed": true
}
```

Fields that are null for the scheme are returned as `null`.

### 5.4 Calculation rules

Weights:

| `gradingScheme` | `midterm` | `project` | `finalExam` |
| --- | --- | --- | --- |
| `MIDTERM_FINAL` | 40% | — | 60% |
| `MIDTERM_PROJECT_FINAL` | 30% | 30% | 40% |
| `PROJECT_ONLY` (DT1) | — | 100% | — |

1. The weighted average is calculated **exactly** and then rounded to a whole number, **half up** (x.5 always rounds up). For example 51.5 → 52 and 84.5 → 85. Results must not be affected by floating-point error.
2. `average` is that rounded whole number (integer).
3. `letterGrade` comes from `average`:

| `letterGrade` | `average` |
| --- | --- |
| `AA` | 85–100 |
| `BA` | 78–84 |
| `BB` | 70–77 |
| `CB` | 63–69 |
| `CC` | 55–62 |
| `DC` | 48–54 |
| `DD` | 40–47 |
| `FF` | 0–39 |

4. `passed` is `true` when `average` ≥ 40, otherwise `false`.

Examples:

| Scheme | midterm / project / finalExam | Exact average | `average` | `letterGrade` | `passed` |
| --- | --- | --- | --- | --- | --- |
| MIDTERM_FINAL | 50 / – / 70 | 62.0 | 62 | CC | true |
| MIDTERM_FINAL | 30 / – / 45 | 39.0 | 39 | FF | false |
| MIDTERM_FINAL | 100 / – / 100 | 100.0 | 100 | AA | true |
| MIDTERM_PROJECT_FINAL | 55 / 50 / 50 | 51.5 | 52 | DC | true |
| MIDTERM_PROJECT_FINAL | 85 / 90 / 80 | 84.5 | 85 | AA | true |
| MIDTERM_PROJECT_FINAL | 30 / 35 / 50 | 39.5 | 40 | DD | true |
| MIDTERM_PROJECT_FINAL | 80 / 90 / 88 | 86.2 | 86 | AA | true |

## 6. Student report

`GET /api/students/{studentId}/report` → 200; 404 if the student does not exist.

### 6.1 Response

```json
{
  "studentId": 1,
  "studentNumber": "220201001",
  "fullName": "Ayşe Yılmaz",
  "courses": [
    {
      "courseId": 1,
      "courseCode": "SE402",
      "courseName": "Engineering Design II",
      "courseType": "THEORETICAL",
      "gradingScheme": "MIDTERM_PROJECT_FINAL",
      "grade": {
        "midterm": 55,
        "finalExam": 50,
        "project": 50,
        "average": 52,
        "letterGrade": "DC"
      },
      "absence": {
        "totalAbsenceHours": 10,
        "allowedAbsenceHours": 13,
        "remainingAbsenceHours": 3,
        "status": "WARNING"
      },
      "result": "PASSED"
    }
  ]
}
```

### 6.2 Rules

1. `fullName` = `firstName` + one space + `lastName`.
2. `courses` contains every course for which this student has **at least one absence record or a grade**, sorted by `courseCode` ascending. If there are none, `courses` is `[]`.
3. `grade` is `null` when no grade has been recorded for that course. Otherwise it contains the same values as the grade result in section 5.3.
4. `absence` is always present and is calculated exactly as in section 4. When the course has a grade but no absence records, `totalAbsenceHours` is 0 and `status` is `NORMAL`.
5. `result` is decided in this order:
   1. `FAILED_ABSENCE` if `absence.status` is `FAILED`
   2. otherwise `INCOMPLETE` if `grade` is `null`
   3. otherwise `FAILED_GRADE` if `letterGrade` is `FF`
   4. otherwise `PASSED`

## 7. Change request DT1: project-only grading

Given to the LLM only after P1–P4 are complete.

- `gradingScheme` gets a third value: `PROJECT_ONLY`.
- For `PROJECT_ONLY` courses: `project` is required; `midterm` and `finalExam` must be null; the average is 100% of `project`.
- The rounding, letter grade, `passed`, report and `result` rules are unchanged and also apply to `PROJECT_ONLY`.
- All existing endpoints and behavior stay the same.

---

## 8. Change request DT2: per-course absence limit

Given to the LLM only after DT1 is complete.

- Courses get a new optional field:

| Field | Type | In request | Rules |
| --- | --- | --- | --- |
| `absenceLimitPercent` | integer or null | optional | 1 to 100 inclusive when present; absent or `null` means "use the default for the course type" |

- `absenceLimitPercent` is accepted by `POST /api/courses` and `PUT /api/courses/{id}` and returned by all course responses (as `null` when not set).
- When it is set, it replaces the type default (`theoreticalLimitPercent` / `practicalLimitPercent`) in step 2 of section 4.4. All other absence rules are unchanged.
- Example: a THEORETICAL course with 3 h/week and `absenceLimitPercent` = 10 → `allowedAbsenceHours` = 42 × 10 / 100 = 4.2 → 5.
- The absence status endpoint and the student report use the course's effective limit.
- All existing endpoints and behavior stay the same.
